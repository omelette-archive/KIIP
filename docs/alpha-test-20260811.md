## 발견한 문제와 처리

### P0 — 전국 검색 결과를 지역 상표 건수로 사용할 수 없음

같은 `noticeName + niceClass` 검색 결과를 해당 품목이 있는 각 지역행에 복제한다. 출원인 주소가
확인되지 않은 hit까지 지역×품목 상표 건수와 대표성 판정에 들어가므로 모든 지역이 비슷하게 큰
상표 건수를 갖고, 이번 실행에서는 공백 알림이 0개가 됐다.

배포 전 필요한 변경:

1. 전국 품목 검색 결과와 지역 귀속 결과를 별도 fact로 저장한다.
2. 지역 상표 건수에는 주소가 `inside`로 검증된 hit만 사용한다.
3. 주소 커버리지가 임계값 미만이면 지역 건수·공백 점수를 `blocked`로 표시한다.
4. 농사로 지역브랜드 연관성은 출원인 주소 대신 사용할 수 없으므로 계속 별도 지표로 둔다.

후속 코드에서는 전국 검색 건수를 `nationwideSearchTrademarkCount` 참고값으로 분리하고,
지역 건수는 출원인 주소가 `inside`로 확인된 `regionalUniqueTrademarkCount`만 사용하도록
변경했다. 검색 수집 또는 저장 hit의 주소 귀속이 하나라도 불완전하면 지역 건수·등록률·공백
점수를 `blocked` 처리한다. 기존 알파 원본을 API 재호출 없이 다시 계산한 결과 668개 전부가
차단되고 랭킹은 0개가 됐다. 잘못된 수치 노출은 막았지만, 실제 지역 통계를 제공하려면 #50의
주소 보강과 query fact 저장구조 변경이 계속 필요하다.

### P0 — 자동 품목 정규화 커버리지 38.9%

1,049건이 사람 검토 대기다. 현재 규칙만으로 전국 원본을 자동 검색하면 원본의 61.0%가 분석에서
빠진다. 검토대기 사유·빈도를 집계해 반복 패턴부터 규칙으로 승격하고, 애매한 항목만 사람이
확인해야 한다. 사용자 확정 전 AI가 임의로 고시명칭을 결정하지 않는 원칙은 유지한다.

후속 승인으로 파프리카·고추류, 방울토마토, 호박류, 메론, 버섯류 10개 표현 묶음을
`approved-aliases.json`에 기록했다. 고시상품명칭 13판의 대상 명칭·NICE류·유사군코드를 실행 시
다시 확인한 뒤에만 `rule_approved_alias`로 확정한다. 실데이터 재실행에서는 공백 변형 1건을
포함해 90건이 추가 확정되어 커버리지가 44.1%로 올랐다. 한우·벌꿀·단감·잡곡 등 미승인
항목은 계속 검토대기에 남겼다. ③ dry-run에서 검색 가능 행은 669→759로 늘었지만 승인 별칭이
기존 표준명으로 합쳐져 고유 KIPRIS 검색어는 125→126개만 증가했다.

### P0 — 등록원부 429와 보강 지속성

직렬 호출에서도 44건 성공 후 429가 발생했고 남은 56건 재시도로 실행이 약 9분 38초 걸렸다.
계정의 당일 잔여량 또는 제공기관 할당량 소진 가능성이 높다. 이번 수정에서 첫 429 이후 후속
호출을 중단하는 회로 차단과 `selected/requested/rate-limit-skipped` 분리 집계를 추가했다.

추가로 등록번호별 응답 캐시·체크포인트와 일별 호출 예산이 필요하다. 현재 11,608개를 한 번에
보강할 수 없다.

### P1 — 부분 수집과 호출량

125개 고유 검색에 605페이지를 사용했다. 현재 승인 계정의 실제 월 호출량은 확인되지 않았으므로 매번 같은 전체 검색을
반복할 수 없다. 체크포인트를 장기 보존하고 신규·변경 검색만 증분 처리해야 한다. `max_pages=5`를
없애는 것만으로는 불필요한 재호출이 커지므로 해결되지 않는다.

2026-08-12 반영: 체크포인트의 `numOfRows`와 `maxHitsPerQuery`가 같을 때 `maxPages` 상한을
늘리면 기존 partial 쿼리를 다음 미수집 페이지부터 재개한다. 상한을 줄이거나 hit 상한을 바꾸는
경우에는 누락 가능성이 있어 계속 차단한다. 고유 검색 조합의 완료·부분·오류 건수도 ③→④→⑦로
자동 전달하므로 대시보드 빌드 때 수동 입력하지 않는다.

  17,087`(검증률 28.8%, 검증 hit 6,911건)로 크게 올랐다. 주소 보강 자체는 더 이상 병목이
  아니다.
- **그런데도 랭킹은 여전히 0** — 736개 지역×품목 전부 `blocked`. 사유를 집계하면 708개(96%)가

## 쿼리당 상한을 대폭 올려 완전 수집 시도(같은 날, 이어서)

세부 예외 규칙(범용어 제외 등)을 먼저 만들지 않고, 쿼리당 hit 상한만 500→10,000(페이지
5→100)으로 크게 풀어 그대로 밀어붙이는 실험을 했다. 결과는 성공이 아니라 **현재 구조의 실제
한계**를 확인한 것에 가깝다.

- **10,000 상한 시도 — 출력 단계에서 충돌**: 126개 쿼리 수집 자체는 API 오류 0으로 끝났다
  (complete 80, partial 46, 체크포인트 297MB). 그런데 지역×품목 행마다 해당 쿼리의 hit
  배열 전체를 복제해 넣는 현재 출력 구조 때문에, 최종 결과 JSON을 한 문자열로 직렬화하는
  단계에서 `Invalid string length`(Node/V8 최대 문자열 길이 초과)로 실패했다. 이미 문서에 적어둔
  P1(③ 출력 중복과 파일 크기)이 실제로 터진 사례다.
- **상한을 낮춰가며 재시도**: 3,000 → 여전히 실패, 1,200 → 여전히 실패, 600 → 성공(출력
  332.8MB). 즉 현재 구조에서 안전하게 쓸 수 있는 실질 상한은 600 안팎이며, 그 이상은 코드
  변경(쿼리 단위 1회 저장 + 참조 구조) 없이는 못 올린다. API를 다시 부르지 않고 이미 받은
  체크포인트를 슬라이스만 해서 재시도했으므로 이 과정에서 추가 KIPRIS 호출은 없었다.
- **600 상한으로 재계산해도 랭킹은 여전히 0**: 출원인 주소는 이번엔 신규로 드러난 출원번호
  13,391개까지 마저 보강해 고유 출원번호 37,302개 전량 캐시 완료(검증률 82.8%, inside
  513·outside 30,587·unverified 6,463 — 0.15%에서 크게 개선). 그런데도 736개 지역×품목 중
  **`collection_incomplete` 없이 완전히 풀린 건 0개**다(둘 다 걸림 693개, 주소만 부족 43개).
  즉 지금 안전장치는 "그 지역×품목에 관련된 모든 쿼리가 100% 완전 수집 + 100% 주소 검증"을
  요구하는 all-or-nothing 기준이라, 대량 hit 품목이 하나라도 섞인 조합은 나머지가 아무리
  좋아져도 절대 안 풀린다.
- **결론**: 상한을 더 올리는 방향은 두 가지 벽에 막혀 있다 — (1) 출력 구조상 ~600~800 근처의
  하드 크래시 한계, (2) 100%가 아니면 무조건 차단하는 완전주의 게이트. 지금 시점에서 랭킹을
  실제로 보려면 둘 중 하나는 바꿔야 한다: 출력을 쿼리 단위 1회 저장으로 재구조화하거나, 게이트를
  임계값 기반(예: 검증률 ≥N%)으로 완화하거나. 둘 다 이번 알파테스트 범위 밖의 설계 결정이라
  여기서 더 밀어붙이지 않고 기록만 남긴다.
