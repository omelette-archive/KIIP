# 신규 Open API 소스 연동 체크리스트

새 정부/공공기관 API를 파이프라인에 붙일 때 반복해서 겪은 시행착오를 순서화한 것이다.
지금까지 붙인 세 소스(KIPRIS, 지리적표시(GI), 농사로) 모두 카탈로그 페이지의 설명과 실제
계약이 달랐다 — "공공데이터포털에 등록돼 있다"는 것이 "표준 포맷을 쓴다"는 뜻이 아니었다.
다음에 새 소스를 붙일 때는 이 순서를 따르면 같은 시행착오를 줄일 수 있다.

## 1. 카탈로그 페이지의 "API 유형"부터 확인한다

data.go.kr 상세페이지의 `API 유형`이 표준 REST(`serviceKey` 쿼리파라미터 +
`response.header.resultCode` 포맷)인지, `LINK`(제공기관 자체 시스템으로 연결만 해주는
타입)인지 먼저 확인한다.

- **실측(GI)**: 지리적표시(`data/15080629`)는 `API 유형: LINK`였다. data.go.kr 표준이라고
  가정하고 `dataGoKrClient.js`(serviceKey/JSON)로 먼저 구현했다가, 실키로 호출해서야
  `[11] 인증키가 등록되지 않았습니다`류 오류로 잘못된 가정이었음을 확인했다. 실제 계약은
  URL 경로에 키가 들어가는 농식품 공공데이터포털(`data.mafra.go.kr`)의 자체 Grid API였다.
- **실측(농사로)**: 카탈로그 설명과 달리 실제로는 `apiKey` 쿼리파라미터 + XML 응답
  (`localSpcprd/localSpcprdLst`)이었다 — 이 역시 data.go.kr 표준이 아니었다.

## 2. LINK 타입이면 제공기관 페이지에서 진짜 엔드포인트를 찾는다

data.go.kr 상세페이지 하단의 제공기관 참고 링크를 따라가면 실제 API 문서가 있다. GI는
`data.mafra.go.kr` 상세페이지의 "OpenAPI 미리보기" 섹션에서 실제 요청 URL 패턴
(`/openapi/{API_KEY}/{TYPE}/{API_URL}/{START_INDEX}/{END_INDEX}`)을 확인할 수 있었다.

## 3. 회원가입/키 발급 전에 공개 테스트 키로 계약부터 검증한다

정부 API 다수가 `API_KEY=sample` 같은 값으로 소량 호출을 인증 없이 허용한다. GI는 `sample`
키로 curl 호출해서 응답 스키마와 필수 파라미터(`REGIST_NO_REGIST_DE` 완전일치)를 회원가입도
하기 전에 미리 확인할 수 있었다. 승인 대기 없이 계약 오판 여부를 가장 빨리 걸러내는 단계다.

## 4. 실키 발급 후엔 curl로 raw 호출 먼저, 클라이언트 코드는 그 다음

문서에 "필수"라고 적힌 파라미터가 실제로 완전일치만 허용하는지, 와일드카드가 되는지는 실제
호출로만 확정된다.

- **실측(GI)**: `REGIST_NO_REGIST_DE`에 연도만 넣으면 에러 없이 0건, 엉뚱한 파라미터명으로는
  "필수 파라미터 누락" 오류, `%` 와일드카드도 0건 — 세 경우를 각각 curl로 찍어보고서야
  "완전일치 날짜만 허용, 전체 목록 조회 자체가 불가능"이라는 데이터 소스의 실제 한계를
  확정했다. 이건 코드로 우회할 수 없는 제약이라, 클라이언트를 다 짜고 나서 발견했으면 재작업이
  훨씬 컸을 것이다.

## 5. 인증 오류가 나면 "키가 틀렸다"로 바로 단정하지 않는다

가능성을 순서대로 배제한다: (1) 이 서비스에 활용신청/승인이 났는가 (같은 계정의 다른 서비스와
혼동하지 않았는가), (2) IP 화이트리스트를 등록했다면 지금 호출하는 환경의 아웃바운드 IP와
일치하는가, (3) 발급 직후라 반영 지연 중인가. 셋 다 "코드 문제"가 아니라 "계정/네트워크 상태"
문제라 클라이언트 코드를 고쳐도 해결되지 않는다.

## 6. quota/제한은 문서 문구를 그대로 인용해서 기록한다 (`docs/open-api-limits.md`)

"제한없음"이라고 적혀 있어도 오류코드 목록에 "요청 초과" 계열 코드가 따로 있으면 그 사실도
같이 적어둔다 — 낙관도 비관도 하지 않고 실제로 확인한 문구만 남긴다.

## 7. `config/sources.json` 레지스트리에 확정 정보를 반영한다

- `authentication.approval`에 승인 방식(자동승인/제공기관 심사/IP 등록 등)을 구체적으로 적는다.
- `implementation.status`를 실측 상태(`live_key_validated` 등)로 갱신해서, 문서만 보고
  넘겨짚은 상태가 레지스트리에 남지 않게 한다.

## 8. `selftest.js`에 실제 응답 구조를 모킹한 회귀 테스트를 추가한다

성공 응답뿐 아니라 "HTTP 200인데 본문 코드는 에러"인 경우(MAFRA의 `INFO-100`, data.go.kr의
`resultCode 30` 등)를 반드시 포함한다. 정부 API는 HTTP 상태코드와 무관하게 200으로 에러를
감싸 보내는 경우가 흔해서, `response.ok`만 보면 에러를 성공으로 오인한다.

## 9. 실키로 소량 E2E를 돌려서 다음 단계까지 스키마가 이어지는지 확인한다

`samples/`의 고정 소량 입력으로 ①→②→③(→④)까지 실제로 관통시켜본다. 필드 하나만 따로 보면
안 보이는 계약 문제(예: 지역 필드가 자유문이라 법정동코드 매칭이 안 되는 경우)가 여기서
드러난다.

## 10. GitHub 이슈에 조사 로그를 남기고, PR의 "검증" 섹션을 채운 뒤 닫는다

"뭘 해야 하는지"가 아니라 "무엇을 실제로 호출해서 무슨 응답을 받았는지"를 이슈 코멘트에
날짜와 함께 남긴다. 다음에 같은 소스를 다시 만지거나 비슷한 신규 소스를 붙일 때, 이 로그가
재조사 시간을 줄여준다 (지리적표시 이슈 #14, PR #15의 코멘트 이력 참고).
