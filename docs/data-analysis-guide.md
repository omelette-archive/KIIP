# 데이터 분석 가이드 — 파이프라인이 실제로 무엇을 하는가

README의 "한 줄 요약"은 진행 상태(🟢/🟡/⚪)를 보여줄 뿐, **무엇을 어떤 기준으로 뽑고,
어떤 근거로 확정하고, 뭐가 아직 사람 판단을 기다리는지**는 각 단계 폴더의 README와 코드
주석에 흩어져 있다. 이 문서는 데이터를 실제로 들여다보거나 대시보드 수치를 해석해야 하는
사람을 위해, 그 흩어진 기준을 한 곳에 모은 것이다. 구현 세부사항은 각 단계 README를,
설계 배경은 `docs/decisions/`와 관련 이슈를 참고한다.

**원칙**: 이 파이프라인은 애매한 판단(원물명 확정, 지정상품 대조, 대표성 판정 등)을
생성형 AI에게 맡기지 않는다. 전부 버전 관리되는 결정론적 규칙이며, 규칙이 자신 없으면
"확정하지 않고 검토대기로 남긴다"가 기본값이다(`docs/decisions/0001-*.md`). 그래서
숫자 하나하나에 "왜 이렇게 나왔는지" 되짚을 수 있는 근거 필드가 항상 붙어 있다 —
아래 각 절의 필드명이 바로 그 근거다.

## 전체 흐름 한 장 요약

```
① 수집          → sido/sigungu/rawItemName (원물 그대로, 미가공)
② 정규화        → noticeName + niceClass (공식 고시상품명칭) 확정 또는 review_required
③ 상표 매칭     → KIPRIS 상표 검색 + 출원인 주소·지정상품 보강
④ 브랜드 분석   → "지역에 귀속된 상표"만 집계, 미검증은 지표 자체를 차단
⑤ 브랜드 공백   → 대표 특산품만 순위·점수 산출
⑥ 전략 제안     → 고정 템플릿 문장(AI 미사용)
⑦ 대시보드      → 위 전부를 하나의 스냅샷으로 결합, 상태·출처·버전을 항상 병기
```

각 화살표에서 "누락"이 아니라 "명시적으로 대기·차단"으로 처리되는 게 이 파이프라인의
핵심 설계다 — 즉 숫자가 낮게 나오는 건 실제로 낮아서가 아니라 아직 검증이 안 됐기
때문일 수 있고, 그 구분이 항상 필드로 남는다.

## ① 수집 — 무엇을, 어디서

| 출처 | 다루는 것 | 한계 |
|---|---|---|
| GI(지리적표시, 국립농산물품질관리원) | 법적으로 등록된 지리적표시 특산품 | 등록일 완전일치 조회만 가능 — 과거 전체 이력을 한 번에 못 받음(#22) |
| 농사로(농촌진흥청) | 지자체가 등록한 지역특산물 카탈로그 | 제주·서울·세종은 이 소스에서 0건(#60) — "실제로 특산물이 없다"가 아니라 "이 소스가 커버 안 함"이라는 뜻이며, `sourceCoverageGaps.json`으로 대시보드에 명시됨 |
| 세종시 공식 특산품 | 읍면동 홈페이지가 명시적으로 `특산품`으로 표시한 항목 | 2026-08-21 검증 스냅샷 7품목; 전국 지자체 일반 크롤러는 아님 |
| 농관원 제주 지리적표시 | 대상지역이 제주특별자치도 일원인 공식 등록품 | 2026-08-21 검증 스냅샷 3품목; 제주 전체 특산품 목록을 뜻하지 않음 |

출력은 원물 그대로(`rawItemName`)이고 아직 아무 가공·정제가 없다. `sourceId`,
`sourceContractVersion`, `sourceFetchedAt`이 매 행에 붙어 어느 출처·어느 계약 버전에서
나왔는지 항상 추적 가능하다. 과거 행정구역을 현재 기준으로 승계한 행은 `sourceRegionName`,
`sourceRegionCode`, `regionCode`, `regionMatchMethod`로 원문과 변환 경로를 함께 남긴다.

## ② 정규화 — 원물명을 공식 품목명으로 바꾸는 기준

**왜 이 단계가 필요한가**: ③에서 KIPRIS 상표를 검색하려면 검색어와 NICE류가 있어야
한다. "매실"이라는 원문 그대로 검색하면 무관한 상표까지 섞이거나 표기 변형을 놓친다.
그래서 먼저 지식재산처 고시상품명칭 사전(13판, 57,549건)과 대조해 공식 품목명을
확정한다.

### 판정 근거(`verdictSource`) — 2026-08-14 실측(원물 1,721건 기준)

| verdictSource | 뜻 | 비중 |
|---|---|---:|
| `exact` | 원물명이 사전과 완전히 동일 — 판단의 여지 없음 | 8.2% |
| `human_approved_alias` | 사람이 승인한 별칭 사전(`data/approved-aliases.json`) 매칭 | 9.2% |
| `algorithm` | 결정론적 접두어 규칙("신선한 X"/"미가공 X")으로 자동 확정 — **사람이 매 건 승인하지 않음**, 대시보드에 "AI 판정" 배지로 구분 표시(생성형 AI 아님, 결정론적 규칙) | 30.6% |
| `excluded` | 나무/묘목/씨앗 등 규칙으로 분석 대상에서 제외 | 0.2% |
| `unresolved` | 검토대기 — 사람 결정 필요 | 51.8% |

재현: `node 02-normalize-items/reportNormalizationDecisions.js --input <normalized.csv>`
(출력 예시: `docs/normalization-decisions-20260818.md`).

### 검토대기 891건이 왜 못 넘어가는지 — 실측 패턴 분해

전체 검토대기를 원물명으로 묶으면 732개 군집이 나오는데, **661개(90%)가 1건짜리
singleton**이라 "상위 몇 개만 보면 대부분 해결"되는 구조가 아니다. 대신 패턴별로 보면:

1. **원물 vs 가공품 불일치(약 200건, 22.6%)** — 매실→매실주, 대추→대추차처럼 원물의
   유일한 사전 후보가 가공품/주류 형태뿐인 경우. 원물과 가공품을 별개 품목으로 볼지,
   가공품 상표도 원물 브랜드 활용 근거로 인정할지가 **아직 업무 기준이 정해지지 않은
   미해결 정책 문제**다 → **[#74](https://github.com/omelette-archive/KIIP/issues/74)**
2. **범주·활동 용어(품목이 아님)** — 잡곡, 양봉, 양돈처럼 단일 NICE류로 대표될 수 없는
   표현. 대부분 사전 후보 자체가 없다(`no_candidates`).
3. **생물/가공 상태 모호** — 멸치→건멸치, 바지락→생 바지락조개처럼 원천 데이터에
   생물·가공 상태 정보가 아예 없어서 어느 사전 항목이 맞는지 구조적으로 알 수 없음.
4. **진짜 사전 공백** — 두릅, 곰취, 매생이, 대파처럼 실재하는 특산품인데 57,549건
   사전에 정말 없는 경우. 사람이 판단해도 답이 없을 수 있다(사전 자체의 공식 개정
   전까지는).
5. **①단계 원문 오염** — ㈜실키안, 능수한우, 뜨레한돈처럼 브랜드/상품명이 원물명
   필드에 섞여 들어간 경우. 이건 ②의 정규화 실패가 아니라 ①(수집) 데이터 정제
   문제다.
6. **문자열 유사도 오탐** — 단감→옷단감치는 기계처럼 후보 검색 로직이 무관한 항목을
   최상위로 제시하는 경우. 확정에는 안 쓰이지만(문자열 점수는 검토용 후보 순위에만
   사용) 검토 화면 품질에는 영향을 준다.

재현: `node 02-normalize-items/summarizeReviews.js --input <review-required.csv>`.

## ③ 상표 매칭 — 무엇을 검색하고 어떻게 지역·품목을 귀속시키는지

- **검색**: KIPRIS `getWordSearch`를 ②가 확정한 고시명칭+NICE류로 호출. NICE류가
  없는(검토대기 원물명으로 참고 검색만 한) 행은 식품 관련 기본류(`29·30·31·32·33·40·43`)로
  좁혀서 검색하고 `classCodeFallbackApplied=true`로 표시한다 — 이건 업무 확정 기준이
  아니라 노이즈 완화용 v1 규칙이다.
- **지역 귀속**: 상표 검색 결과 자체에는 출원인 주소가 없다. 등록번호가 있으면
  등록원부(`getMarkHistory`), 없으면 출원 속보(`trademarkApplicantInfo`)로 주소를 보강해
  법정동코드 마스터와 대조한다. **농사로 지역브랜드(`areaBrandLst`) 출원번호 조인은
  지역 귀속 근거가 아니다** — 브랜드-지역 연관성 참고 지표일 뿐, 출원인 주소만이
  `applicantRegionMatch=inside/outside/unverified`의 근거다.
- **지정상품 대조(#12)**: 등록번호가 있는 hit만 등록원부에서 지정상품명을 받아
  `normalized_exact`/`normalized_contains`(둘 다 확정 인정) vs `class_only`(사람 검토
  후보) vs `mismatch`/`unverified`로 분류한다. **등록번호가 없는 출원(심사중·거절)은
  이 대조 자체가 안 된다** — KIPRIS 응답에 출원번호 기준 지정상품 조회 수단이
  확인되지 않았기 때문(`docs/kipris-api-notes.md`). 이 경우 몇 건이 지정상품 근거 없이
  NICE류·주소만으로 집계되는지는 ④의 경고 문구로 노출된다.

## ④ 브랜드 분석 — "지역에 귀속된 상표"로 인정하는 기준

- **지역 지표 게이트**: 지역×품목 행의 검색이 완료(`collection_incomplete`가 아님)되면
  주소 확보율과 무관하게 확보된 값 그대로 공개한다(2026-08-14 정책 변경 — 이전엔 주소
  확보율 60% 미만이면 전부 차단했음). 확보율은 참고 지표로만 병기한다.
- **핵심 지표**: `localApplicantShare`(출원인 주소가 검증된 hit 중 지역 내부 비율),
  `registrationRate`(지역 inside 확정 출원 중 등록 상태 비율) — 둘 다 `applicantRegionMatch`
  근거만 사용하고, 주소 미검증 hit는 분모·분자 어디에도 안 들어간다.
- **경고(warnings) 메커니즘**: 등록원부 429/일일예산 소진, 지정상품 미평가 건수,
  소스 커버리지 공백(제주 등) 같은 데이터 품질 문제는 전부 이 단계의 `warnings` 배열에
  쌓여서 ⑦ 대시보드 "출처와 데이터 상태" 섹션에 그대로 노출된다 — 별도 대시보드 코드
  변경 없이 새 경고를 추가하면 자동으로 화면에 뜨는 구조다.

## ⑤ 브랜드 공백 발굴 — 대표 특산품과 점수

- **대표 특산품 판정(2026-08-11, #29 확정)**: GI 출처 등록 **또는** 상표 출원 3건
  이상이면 대표 특산품으로 본다. 대표가 아니면 순위·공백 점수 자체를 계산하지 않는다.
- **공백 점수(`gap-score-v2-regional-address-gate`)**: 활용도(출원 활동량, 상한 5건을
  포화로 간주) 70% + 등록 성사율 30%로 계산 — **이 가중치와 포화 기준은 실측 근거 없는
  잠정값**이며, 업무 기준이 정해지면 `05-detect-brand-gap/lib/scorer.js` 한 파일만
  바꾸면 된다. `scoreVersion`을 보면 어떤 기준으로 나온 점수인지 항상 구분된다.

## ⑥ 전략 제안 — 고정 템플릿

⑥-1은 생성형 AI를 쓰지 않는 고정 템플릿 문장 생성이다. ⑥-2(개별 AI 검토)는 원본과
분리된 별도 승인 흐름으로 설계됐고(#16), 사람 승인 전에는 자동 반영되지 않는다.

## ⑦ 대시보드 — 화면에 뭐가 나오고 뭐가 아직 막혀 있는지

- `mode=sample`(고정 소량)과 `mode=full`(전체 범위 시도, 완전 수집 보장 아님)을 항상
  구분해 표시한다.
- 모든 지표는 `availability`(available/preview/blocked)와 `blockingIssue`(관련 이슈
  번호, 예 `#50`/`#12`/`#29`)를 갖는다 — 화면에 숫자가 안 보이면 이유와 관련 이슈로
  바로 연결된다.
- 지도 렌더링은 행정구역 경계 GeoJSON이 아직 안 붙어서 차단 상태다.
- 품목 라벨은 상표명이 아니라 ② 표준 특산품명이다. 개별 상표명·지정상품 근거는
  "관련 출원 상표 사례"에 별도로 남는다.

## 직접 재현해보고 싶을 때

```bash
node scripts/validatePipeline.js                      # 전 구간 계약 검증(키 불필요)
node 02-normalize-items/reportNormalizationDecisions.js --input <normalized.csv>
node 02-normalize-items/summarizeReviews.js --input <review-required.csv>
```

각 단계 폴더의 `README.md`에 CLI 옵션·입출력 스키마 전체가 있다. 원본 제공기관·공식
URL·계약 확인일은 `docs/data-source-provenance.md`가 중앙 관리한다.
