# ADR 0001: ②단계는 결정론적 규칙과 수동 검토로 운영한다

- 상태: 승인됨
- 결정일: 2026-08-07
- 범위: `02-normalize-items/`

## 배경

특산품 원문을 고시상품명칭과 NICE 분류로 매핑할 때 의미가 애매하거나 후보가 여러 개인 행이
생긴다. 외부 LLM API가 이 판단을 자동으로 수행하면 같은 입력의 결과가 달라질 수 있고,
프롬프트·모델·비용·키에 의존하며 잘못된 매핑의 근거를 재현하기 어렵다.

## 결정

②단계의 자동 처리는 버전 관리되는 규칙과 고시명칭 사전만 사용한다. 정확히 하나로 확정되지
않는 행은 `review-required.csv` 중간산출물로 분리한다. 외부 생성형 AI, Claude 또는
Anthropic API를 정규화·후보 선택·검토 승인에 사용하지 않는다.

사람의 결정은 다음으로 제한한다.

1. 생성된 후보 중 하나 승인
2. 분석 대상 제외
3. 보류

승인과 제외에는 검토자와 검토 시각을 필수로 남긴다. 후보에 없는 매핑은 CSV에 임의 입력하지
않고, 반복 사례를 확인한 뒤 명시적 사전/규칙과 자체 테스트로 승격한다.

## 구현과 저장

- `normalizeItems.js`: 규칙 결과, `inputIndex`, 후보, 빈 감사 필드를 생성
- `applyManualReviews.js`: 사람이 기록한 제한된 결정을 검증하고 전체 결과에 병합
- 현재 저장: 원본/검토/병합 CSV 중간산출물
- DB 도입 후: `normalization_reviews`에 결정, 후보 인덱스, 근거, 검토자, 시각을 append-only 저장

③단계는 `status=ok`인 행만 상표 검색 대상으로 사용한다. 따라서 미검토·보류 행이 자동으로
다음 단계에 유입되지 않는다.

## 구현 갱신 — 2026-08-18: 판정 출처 표시와 사후 감사 리포트(#51)

이 ADR이 금지하는 것은 "같은 입력에 다른 결과가 나올 수 있는 비결정론적 외부 LLM 호출"이지,
"사람이 매 건 개별 승인하지 않고 버전 관리된 결정론적 규칙이 자동 확정하는 것" 자체가 아니다 —
`rule_fresh`/`rule_unprocessed`(신선한/미가공 접두어 화이트리스트)는 처음부터 이 방식으로
동작해왔다. 다만 지금까지는 이 자동 확정이 `rule_exact`(문자 그대로 동일)와 구분 없이 노출돼
"사람이 승인했다"와 "규칙이 추정했다"를 구분할 수 없었다.

- `verdictSource` 필드(`exact`/`human_approved_alias`/`algorithm`/`excluded`/`unresolved`/`error`)를
  ②→③→④→⑦ 전 구간에 전파하고, ⑦ 대시보드는 `algorithm` 판정에 "AI 판정" 배지를 표시한다
  (규칙 기반 결정론적 알고리즘이며 생성형 AI 호출이 아니다).
- `node 02-normalize-items/reportNormalizationDecisions.js`가 전체 정규화 결과를 판정
  출처별로 집계하고, `algorithm` 판정 원물명→고시명칭 조합을 사후 표본검사용 목록으로 남긴다.
- 화이트리스트에 새 접두어를 추가하는 것은 여전히 "코드/사전 변경 + 자체 테스트"로만
  가능하다(본 ADR의 자동화 확장 경로를 그대로 따름). 이 리포트는 그 확장 여부를 판단할
  근거를 사람에게 제공하는 용도이며, 화이트리스트를 우회해 신뢰도만으로 자동 확정 범위를
  넓히지 않는다.

## 영향

- API 키와 모델 가용성 없이 동일 입력에 동일 자동 결과를 얻는다.
- 애매한 데이터는 사람이 확인하므로 처리량보다 정확성과 추적 가능성을 우선한다.
- 반복 검토 사례는 코드/사전 변경과 테스트를 통해서만 자동화 범위에 포함된다.
- ⑥-1은 고정 템플릿으로 구현한다. ⑥-2 생성형 AI 개별 검토는 원본과 분리하고 사람 승인 전에는
  자동 반영하지 않는 별도 범위로 관리한다(#16).
